# Сборка сервера в GitHub Actions

Workflow: [server.yml](../../.github/workflows/server.yml).
Сервер и клиент выпускаются независимо: версия сервера берётся из
`server/Cargo.toml`, протокол — из `cc-protocol`. Workflow не изменяет протокол,
не переносит PostgreSQL и не подключается к рабочим серверам.

## Что проверяется

1. Форматирование, Clippy, тесты протокола и сервера с PostgreSQL 16.
   `CC_TEST_REQUIRE_DB=1` запрещает тихо пропустить интеграционные проверки;
   инструменты PostgreSQL доступны для настоящего `pg_dump`/`pg_restore`.
2. Защита публикации: соответствие версии тегу, допустимый репозиторий,
   наличие обеих архитектур и корректные immutable digest образов.
3. Нативная Docker-сборка на GitHub-hosted `ubuntu-24.04` и
   `ubuntu-24.04-arm`. Собственные клиентские runners для неё не нужны.
4. Каждый собранный образ запускается в отдельном временном Compose-проекте.
   Проверяются HTTP API, HTTPS через локальный тестовый CA, роли БД, миграции,
   backup/restore, сохранность после перезапуска и отсутствие паролей в логах.
5. Проверенные образы объединяются в multi-platform manifest и публикуются
   в `ghcr.io/evsikovas/consolecrypt-server`.

## Доступы

Внешние pull requests получают только `contents: read` и выполняют проверки
на временных GitHub-hosted runners. Публикация работает только в исходном
репозитории для `main` или `server-vX.Y.Z`; права `packages: write` выдаются
только соответствующим заданиям. Actions закреплены полными Git SHA.

Для GHCR используется автоматический `GITHUB_TOKEN`. Отдельный PAT, SMTP-пароль,
SSH-ключ рабочего сервера и Kubernetes config в Actions не нужны. После первой
публикации владелец должен проверить, что пакет `consolecrypt-server` открыт
для публичного скачивания: видимость нового пакета настраивается отдельно
от видимости исходников.

## Сборка и выпуск

Push в `main` или ручной запуск workflow на `main` создаёт candidate-образ:

```text
ghcr.io/evsikovas/consolecrypt-server:sha-<full-git-commit>
ghcr.io/evsikovas/consolecrypt-server:<version>-<first-12-commit-characters>
```

После проверки версии и успешного candidate-пайплайна создайте релизный тег
на нужном коммите; например, для сервера 0.1.12:

```sh
git tag -a server-v0.1.12 -m 'ConsoleCrypt Server 0.1.12'
git push origin server-v0.1.12
```

Пайплайн повторяет проверки и добавляет теги `0.1.12` и `latest` только при
успехе обеих архитектур. Тег должен точно совпадать с `server/Cargo.toml`.
Повторный запуск может пересобрать образ с новым базовым образом; поэтому
даже для ссылки с Git SHA источником истины является **digest** в артефакте
`server-image/server-image.json`, а не имя Docker-тега.

Укажите `image` из этого JSON как `CC_SERVER_IMAGE` в приватном `server.env`,
а `source_url` как `CC_SOURCE_CODE_URL`. Это сохраняет соответствие AGPL-ссылки
реальному коммиту. Обновление выполняется отдельно, после резервной копии,
по [HOSTING.md](../../docs/public/HOSTING.md).

Новый публичный адрес API — `https://sync.consolecrypt.dev`; сайт и руководство
находятся на `https://consolecrypt.dev`. Собственные установки используют свои
домены. Пример Compose не требует Timeweb, GitHub или доступа к публичному API
ConsoleCrypt во время работы.

## Почта

SMTP настраивается только при запуске контейнера через приватные переменные
`CC_MAIL_FROM`, `CC_SMTP_HOST`, `CC_SMTP_PORT`, `CC_SMTP_TLS`,
`CC_SMTP_USERNAME`, `CC_SMTP_PASSWORD`. Пересборка образа для смены реквизитов
не нужна. Проверки CI используют тестовую почту и не отправляют реальные письма.
Перед переносом публичного сервера проверьте, что провайдер VPS разрешает
исходящие SMTP-соединения: успешный запуск API не доказывает доставку кодов
подтверждения и восстановления.
