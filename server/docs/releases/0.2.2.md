# ConsoleCrypt Server 0.2.2

## Квоты и лимиты запросов

- **Лимиты запросов** в PostgreSQL (token bucket по времени базы), одинаковые
  на любом числе реплик: отправка изменений, удаления, общий доступ, поиск
  получателя, добавление устройств, запросы доверия, сверка ключей, смена
  пароля, WebSocket-подключения, вход и восстановление. Превышение — `429
  rate_limited` с `Retry-After` и `details.limit`; клиент повторяет запрос
  позже. Каждый лимит настраивается ключами `CC_LIMIT_<ИМЯ>_RATE|BURST|PER_HOUR|PER_DAY`
  (в Helm — `config.rateLimit.limits`).
- По умолчанию **`CC_RATE_LIMIT_MODE=observe`**: запросы не отклоняются,
  превышения только считаются (`cc_rate_limit_observed_total`, событие аудита
  `limit_exceeded`). Понаблюдайте неделю и переключите на `enforce`. Лимиты
  входа и восстановления действуют в обоих режимах.
- **Квоты** (`CC_QUOTAS_V2_ENABLED`, по умолчанию включено): число объектов и
  надгробий в хранилище (`CC_MAX_VAULT_OBJECTS`, `413 object_limit`),
  надгробия учитываются в квоте места (`CC_TOMBSTONE_COST_BYTES`); удаление
  объекта, которого на сервере не было, ничего не создаёт. Удаление живого
  объекта проходит всегда.
- **Лимиты устройств**: не больше `CC_MAX_DEVICES_PER_ACCOUNT` (20) активных и
  `CC_NEW_DEVICES_PER_ACCOUNT_PER_DAY` (10) новых устройств в сутки на аккаунт —
  вход с ещё одного нового устройства получает `403 device_limit` /
  `device_daily_limit` (пароль, OIDC, LDAP). Известные устройства входят как
  обычно.
- **Защита от блокировки входа**: считаются только неудачные попытки, по почте
  и сети (/24 IPv4, /64 IPv6) и по почте в целом; вход с известного устройства
  аккаунта лимиты почты не ограничивают, так что чужой перебор не запирает
  владельца. Владелец получает одно письмо в сутки о множестве неудачных
  попыток. Письма сброса пароля ограничены на почту и сеть.
- **Команды администратора**: `admin limits show|set|reset --email …` —
  переопределения лимитов и квот для отдельного аккаунта без перезапуска.
  Метрики `cc_rate_limited_total`, `cc_quota_rejected_total` и другие.

## Доверие к ключам хранилищ

- **Подписанные отпечатки ключей хранилищ** (`PUT|GET
  /v1/vaults/{id}/key-commitments`): каждое устройство публикует подписанное
  обязательство на ключ хранилища, и другие устройства аккаунта замечают
  подменённый ключ. Сервер проверяет подписи и ничего не расшифровывает.
- **Одобрение устройств v2**: подпись одобрения покрывает ключи обоих
  устройств, отпечаток ключа и хэш конверта каждого хранилища; сервер проверяет
  обе подписи и передаёт одобрение новому устройству.
- **Объявление одобряющего устройства** (`POST
  /v1/devices/{id}/approval-intent`, событие `device_approval_intent`): новое
  устройство заранее получает ключи одобряющего, и оба показывают общий код
  сопряжения v2.
- Объявления и записи отпечатков ограничены лимитом `verification_account`
  (20 в час на аккаунт).

## Миграции

- `0013_quotas_limits`: счётчики объектов и надгробий (один раз
  пересчитываются при старте — на больших базах это может занять время),
  таблицы лимитов и переопределений.
- `0014_vault_key_trust`: объявления одобряющих устройств, одобрения v2 и
  записи отпечатков ключей.

по-прежнему (v1).

## English

### Quotas and request limits

- **Request limits** in PostgreSQL (token buckets on the database clock),
  shared by any number of replicas: pushes, deletes, sharing, recipient
  lookup, device enrollment, trust requests, key verification, account
  security, WebSocket connects, sign-in and recovery. Over the limit: `429
  rate_limited` with `Retry-After` and `details.limit`; clients retry later.
  Every limit is tunable with `CC_LIMIT_<NAME>_RATE|BURST|PER_HOUR|PER_DAY`
  (Helm: `config.rateLimit.limits`).
- **`CC_RATE_LIMIT_MODE=observe` by default**: nothing is refused, excesses
  are only counted (`cc_rate_limit_observed_total`, `limit_exceeded` audit
  events). Watch for a week, then switch to `enforce`. Sign-in and recovery
  limits apply in both modes.
- **Quotas** (`CC_QUOTAS_V2_ENABLED`, on by default): live objects plus
  tombstones per vault (`CC_MAX_VAULT_OBJECTS`, `413 object_limit`),
  tombstones count against the byte quota (`CC_TOMBSTONE_COST_BYTES`); a
  delete of an object the server never had creates nothing. Deleting a live
  object is always accepted.
- **Device limits**: at most `CC_MAX_DEVICES_PER_ACCOUNT` (20) active and
  `CC_NEW_DEVICES_PER_ACCOUNT_PER_DAY` (10) new devices per account per day —
  a sign-in from one more new device gets `403 device_limit` /
  `device_daily_limit` (password, OIDC, LDAP). Known devices sign in as usual.
- **Sign-in lockout protection**: only failed attempts count, per e-mail and
  network (IPv4 /24, IPv6 /64) and per e-mail overall; a sign-in from a known
  device of the account is not held back by the e-mail limits, so someone
  else's guessing cannot lock the owner out. The owner gets at most one
  "many failed sign-ins" mail a day. Password reset mails are limited per
  e-mail and network.
- **Admin CLI**: `admin limits show|set|reset --email …` — per-account limit
  and quota overrides without a restart. Metrics `cc_rate_limited_total`,
  `cc_quota_rejected_total` and more.

### Vault key trust

- **Signed vault key fingerprints** (`PUT|GET
  /v1/vaults/{id}/key-commitments`): every device publishes a signed
  commitment to the vault key, so the other devices of the account notice a
  substituted key. The server verifies signatures and decrypts nothing.
- **Device approval v2**: the approval signature covers both devices' keys,
  the key commitment and the envelope hash of every vault; the server checks
  both signatures and hands the approval to the new device.
- **Approver announcement** (`POST /v1/devices/{id}/approval-intent`, event
  `device_approval_intent`): the new device learns the approving device's
  keys up front and both show a mutual pairing code v2.
- Announcements and fingerprint records share the `verification_account`
  limit (20 per hour per account).

### Migrations

- `0013_quotas_limits`: object and tombstone counters (recounted once at
  start-up — this can take a while on large databases), limit and override
  tables.
- `0014_vault_key_trust`: approver announcements, v2 approvals and key
  fingerprint records.

### Self-hosting docs

- The Docker Compose and Helm examples follow the server release: one
  `CC_SERVER_VERSION` variable (image
  `ghcr.io/evsikovas/consolecrypt-server:<version>`) and the chart
  `appVersion` (chart 0.3.0); the release tag checks that every example
  points at it.
- [HOSTING.md](../../../docs/public/HOSTING.md): current feature table, quotas
  and limits with all keys, version-neutral install and upgrade steps, a
  private `compose.override.yaml`.
- [ENTERPRISE.md](../../../docs/public/ENTERPRISE.md): the override-file recipe
  works with a second `-f`, absolute secret paths and UID 65532 ownership.

Protocol **1.11** only adds fields, routes and `capabilities.vrk_commitment`;
clients of protocol 1.10 and older keep working and approve devices as before
(v1).
